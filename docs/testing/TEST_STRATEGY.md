# Стратегия тестирования (Test Strategy)
## BaseNode Platform

Версия: 1.0  
Статус: Обязательный архитектурный стандарт  
Применяется к: Всем доменам и интеграциям  

---

# 1. Назначение документа

Этот документ определяет:

- уровни тестирования
- обязательные типы тестов
- требования к тестированию Event Sourcing
- тестирование OFFLINE и конфликтов
- критерии допуска релиза

Главный принцип:

Система должна быть воспроизводимой через replay событий.

Если replay ломается — релиз запрещён.

---

# 2. Уровни тестирования

## 2.1 Unit-тесты (Агрегаты)

Тестируется:

- команды
- инварианты
- создание событий
- проверка версии
- отклонение некорректных команд

Формат теста:

Given (история событий)  
When (команда)  
Then (ожидаемое событие или ошибка)

---

## 2.2 Aggregate Replay Test (Обязательный)

Каждый агрегат должен:

- корректно восстанавливаться из истории
- воспроизводить одинаковое состояние при повторном replay
- быть детерминированным

Запрещено:

- зависимость от текущего времени без фиксации
- зависимость от внешних сервисов

---

## 2.3 Concurrency Tests

Проверяется:

- конфликт версий
- отклонение команды при расхождении version
- отсутствие silent overwrite

Обязателен тест:

- параллельные команды
- попытка конкурентного изменения

---

## 2.4 Conflict Tests

Для каждого типа конфликта из CONFLICT_CATALOG:

- создаётся тест
- проверяется событие конфликта
- проверяется отсутствие автокоррекции
- проверяется требование явного разрешения

---

## 2.5 OFFLINE Tests (Критично)

Тестируется:

- создание OFFLINE-событий
- сохранение порядка
- детерминированный event_id
- повторный запуск reconciliation
- отсутствие silent rollback
- создание конфликтов при расхождении

Каждый домен, работающий OFFLINE, обязан иметь отдельные тесты.

---

## 2.6 Idempotency Tests

Проверяется:

- повторная обработка одного external_event_id
- отсутствие изменения состояния при повторе
- устойчивость к двойной доставке

Обязателен тест:

- двойная отправка webhook
- повтор reconciliation

---

## 2.7 Integration Tests

Для:

- PMS
- Кассы
- 1С
- Zabbix
- API

Тестируется:

- формат входящих данных
- обработка устаревших данных
- обработка отказов
- корректность ACL

---

## 2.8 Read-model Tests

Проверяется:

- корректность проекции
- возможность пересборки
- отсутствие бизнес-логики
- обработка lag

Read-model должен пересобраться полностью без ошибок.

---

## 2.9 Closed Period Tests

Для Finance и HR:

- попытка backdate
- корректировка в новом периоде
- защита закрытого периода

Backdate должен отклоняться.

---

# 3. Обязательный набор тестов для каждой новой функции

Каждая новая функция обязана иметь:

[ ] Happy Path  
[ ] Concurrency Path  
[ ] Conflict Path  
[ ] Offline Path (если применимо)  
[ ] Duplicate Event Path  
[ ] Closed Period Attempt (если применимо)  
[ ] Replay Test  

Если хотя бы один отсутствует — PR не принимается.

---

# 4. Нефункциональные тесты

## 4.1 Производительность

- запись события
- replay агрегата
- rebuild read-model
- синхронизация OFFLINE

---

## 4.2 Надёжность

- падение интеграции
- повторная попытка доставки
- частичный сбой во время reconciliation

---

## 4.3 Масштабируемость

- большой объём событий
- параллельная нагрузка
- рост количества агрегатов

---

# 5. Smoke Tests после деплоя

После релиза проверяется:

- создание события
- replay агрегата
- read-model обновляется
- OFFLINE очередь работает
- PMS синхронизация корректна
- нет резкого роста конфликтов

---

# 6. Тестирование Breaking Changes

Если релиз — major:

- replay всей истории обязателен
- upcasting обязателен
- проверка всех интеграций
- проверка OFFLINE-сценариев
- проверка закрытых периодов

---

# 7. Автоматизация

Обязательно:

- запуск тестов в CI
- запрет merge при падении
- проверка покрытия агрегатов
- тест replay на уровне CI

Рекомендуется:

- nightly full replay test
- нагрузочное тестирование перед major release

---

# 8. Что запрещено

Запрещено:

- отключать тест конфликта
- отключать тест OFFLINE
- тестировать только happy path
- игнорировать concurrency
- считать read-model источником истины

---

# 9. Приоритеты тестирования

1. Replay
2. Конфликты
3. OFFLINE
4. Версионность
5. Интеграции
6. Производительность

Если тесты конфликтуют с дедлайном —
переносится дедлайн, а не тесты.
