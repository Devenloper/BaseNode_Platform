# Журнал изменений (Changelog)
## BaseNode Platform

Формат основан на принципах:
- Явная фиксация изменений
- Прозрачность архитектурного влияния
- Отсутствие скрытых изменений
- Соответствие Versioning Policy

---

# Как вести CHANGELOG

1. Каждая версия фиксируется отдельным блоком.
2. Используется семантическая версия (MAJOR.MINOR.PATCH).
3. Указывается дата релиза.
4. Отдельно фиксируются:
   - Новые события
   - Изменения событий
   - Новые конфликты
   - Изменения интеграций
   - Изменения API
   - Миграции
5. Любое архитектурное изменение должно ссылаться на ADR.

# Пример записи

## [1.4.0] - 2026-02-08

### Added
- Событие LoyaltyPointsExpired
- Конфликт LOYALTY_EXPIRATION_CONFLICT

### Changed
- Расширено событие LoyaltyPointsAccrued (добавлено поле expiration_date)
- Обновлён read-model LoyaltySummary

### Fixed
- Исправлена ошибка двойного начисления при OFFLINE-синхронизации

### Migration Notes
- Требуется upcasting LoyaltyPointsAccrued v1 → v2
- Пересборка read-model LoyaltySummary обязательна

### Impact Analysis
- Домен: Loyalty
- Интеграции: не затронуты
- OFFLINE: проверено
- ADR: ADR-014

# Правила

1. Нельзя выпускать релиз без записи в CHANGELOG.
2. Нельзя вносить архитектурные изменения без ссылки на ADR.
3. Нельзя скрывать breaking change.
4. Нельзя изменять историю предыдущих записей.
5. CHANGELOG — часть архитектурной дисциплины.
