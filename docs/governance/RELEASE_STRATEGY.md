# Стратегия релизов (Release Strategy)
## BaseNode Platform

Версия документа: 1.0  
Статус: Обязательный операционный стандарт  
Применяется к: Всем релизам системы  

---

# 1. Назначение документа

Этот документ определяет:

- типы релизов
- правила выпуска изменений
- стратегию миграций
- работу с событиями и версиями
- требования к тестированию
- порядок внедрения в production

Главный принцип:

История событий важнее скорости релиза.

---

# 2. Типы релизов

## 2.1 Patch Release (x.y.Z)

Исправления:

- баги
- тесты
- read-model
- не меняют события
- не меняют API-контракты

Breaking changes запрещены.

---

## 2.2 Minor Release (x.Y.z)

Допустимо:

- добавление новых событий
- добавление новых команд
- добавление новых агрегатов
- добавление новых полей (необязательных)
- расширение API

Breaking changes запрещены.

---

## 2.3 Major Release (X.y.z)

Допустимо:

- изменение архитектурных контрактов
- новая версия API
- новая версия интеграции
- изменение структуры события (через новую версию)
- изменение фундаментальных правил (только через ADR)

Обязателен ADR.

---

# 3. Правила выпуска

Перед релизом:

[ ] Обновлён CHANGELOG  
[ ] Обновлена документация  
[ ] Обновлён BOUNDED_CONTEXT_MAP (если требуется)  
[ ] Обновлён CONFLICT_CATALOG (если требуется)  
[ ] Проверена совместимость событий  
[ ] Проверен replay истории  
[ ] Пройдены OFFLINE-сценарии  

Если хоть один пункт не выполнен — релиз откладывается.

---

# 4. Политика изменений событий

## 4.1 Запрещено

- удалять события
- изменять payload существующего события
- менять смысл события
- переписывать историю

---

## 4.2 Разрешено

- добавить новую версию события
- добавить новое необязательное поле
- реализовать upcasting
- добавить новое событие

---

# 5. Миграции

## 5.1 Миграция read-model

Разрешено:

- пересборка проекций
- изменение структуры read-model

Read-model не является источником истины.

---

## 5.2 Миграция агрегата

Если добавлено поле:

- значение должно быть выводимо из событий
- replay должен корректно восстановить состояние

Запрещено:

- массовое изменение Event Store
- изменение исторических событий

---

# 6. Стратегия деплоя

Рекомендуется:

- Blue-Green deployment
или
- Rolling update

Важно:

Новая версия должна корректно работать со старыми событиями.

---

# 7. Release Flow

1. Завершение разработки
2. Обновление документации
3. Прохождение AI_DEVELOPMENT_CHECKLIST
4. Проверка replay всей истории
5. Проверка OFFLINE_RECONCILIATION_FLOW
6. Проверка конфликтных сценариев
7. Tag версии
8. Deployment
9. Мониторинг

---

# 8. Тестирование перед релизом

Обязательно:

- Replay test (полное воспроизведение истории)
- Concurrency test
- Offline sync test
- Integration test (PMS)
- Idempotency test
- Closed period test

Если любой тест падает — релиз запрещён.

---

# 9. Работа с OFFLINE в релизах

Если релиз затрагивает:

- синхронизацию
- версии агрегатов
- конфликтную модель

Требуется:

- отдельный тест сценария с OFFLINE
- проверка отсутствия silent rollback
- проверка детерминированности

---

# 10. Breaking Changes

Breaking change допускается только если:

1. Создан ADR
2. Обновлена версия API
3. Есть план миграции
4. Обновлена документация
5. Проведён анализ влияния на домены

Без этих пунктов breaking change запрещён.

---

# 11. Changelog

Каждый релиз обязан содержать:

- список добавленных событий
- список изменённых событий
- список новых конфликтов
- список изменений интеграций
- список изменений API

Формат — отдельный CHANGELOG.md.

---

# 12. Мониторинг после релиза

После deployment:

- проверка ошибок Event Store
- проверка задержки read-model
- проверка конфликтов
- проверка синхронизации PMS
- проверка OFFLINE-очереди

---

# 13. Экстренный релиз (Hotfix)

Допускается если:

- исправляется критический баг
- не меняются события
- не меняется контракт API

Hotfix не может:

- менять Event Store
- переписывать историю
- обходить архитектурные инварианты

---

# 14. Приоритеты

При конфликте интересов:

1. Целостность истории
2. Консистентность данных
3. Предсказуемость поведения
4. Производительность
5. Удобство пользователя

---

# 15. Запрещено

Запрещено выпускать релиз, который:

- переписывает события
- объединяет домены без ADR
- меняет источник истины
- вводит silent override
- нарушает Versioning Policy
