# Архитектурный манифест для ИИ-разработки
## BaseNode Platform

Версия: 1.0  
Статус: Обязателен  
Область действия: Вся разработка с использованием ИИ  

---

# 1. Назначение

Данный документ фиксирует неизменяемые архитектурные ограничения,
которые обязательны при любой разработке с использованием ИИ.

ИИ — инструмент.  
Архитектура — закон.

Любое предложение, нарушающее данный манифест, считается недопустимым.

---

# 2. Базовая архитектура

Система построена на принципах:

- Domain-Driven Design (DDD)
- Event Sourcing
- CQRS
- Append-only Event Store
- Anti-Corruption Layer
- Outbox Pattern
- Eventual Consistency

Все проектные решения обязаны соответствовать этой модели.

---

# 3. Абсолютные инварианты

Следующие правила не подлежат обсуждению:

1. События неизменяемы.
2. События не удаляются.
3. Нет прямых UPDATE доменных данных.
4. Нет «тихих исправлений».
5. Нет двойного источника истины.
6. Конфликты не скрываются.
7. Override возможен только через событие.
8. Backdate (задняя дата) запрещён.
9. Одна команда изменяет только один агрегат.
10. Бизнес-логика запрещена в read-model.

Если решение нарушает хотя бы один пункт — оно недопустимо.

---

# 4. Правило источника истины

- Проживание и сумма ACCOMMODATION → PMS
- Услуги → локальная система
- Лояльность → локальная система
- HR → локальная система
- ДГУ → локальная система

Недоступность PMS не делает локальную систему источником истины.

---

# 5. Идемпотентность обязательна

Все внешние события обязаны:

- содержать уникальный external_event_id
- обрабатываться строго один раз
- не менять состояние при повторной обработке

OFFLINE-синхронизация также обязана быть идемпотентной.

Исключений нет.

---

# 6. Принцип компенсации

Любая корректировка реализуется только через компенсирующее событие.

Запрещено:
- редактировать уже сохранённые события
- переписывать историю
- мутировать состояние напрямую

Компенсирующее событие обязано ссылаться на исходное.

---

# 7. Дисциплина версионности

Каждый агрегат имеет поле version.

Команда обязана проверять ожидаемую версию.

При несовпадении:
→ создаётся событие конфликта версий.

Silent-перезапись состояния запрещена.

Синхронизация с PMS обязана соблюдать принцип монотонности версии.

---

# 8. OFFLINE-дисциплина

- OFFLINE-события являются юридически значимыми.
- OFFLINE-события не откатываются автоматически.
- После синхронизации возможен Conflict.
- Silent rollback запрещён.

---

# 9. Защита закрытых периодов

После закрытия отчётного периода:

- нельзя создавать события задним числом
- нельзя изменять исторические факты
- допускаются только корректирующие события в новом периоде

---

# 10. Лояльность

- Баллы не являются деньгами.
- Баланс не может стать отрицательным.
- Конкурентный доступ защищается версией агрегата.
- Silent-перезапись баланса запрещена.
- Ретроспективный пересчёт запрещён.

---

# 11. Что ИИ запрещено предлагать

ИИ не должен предлагать:

- прямые изменения в БД
- админскую кнопку «исправить»
- отключение конфликтов
- временные обходные флаги
- объединение доменов
- бизнес-логику в проекциях
- silent override
- пересчёт истории
- изменение закрытых периодов

Если такое предложение возникает, ИИ обязан явно указать:

> «Это требует изменения архитектурного фундамента».

---

# 12. Обязательная структура ответа ИИ

При проектировании домена или функции ИИ обязан предоставить:

1. Состояние агрегата
2. Список команд
3. Список событий
4. Перечень инвариантов
5. Сценарии конфликтов
6. OFFLINE-поведение
7. Проверку соответствия данному манифесту

---

# 13. Роль ИИ в проекте

ИИ является:

- помощником по проектированию доменов
- генератором структур
- помощником по тест-сценариям

ИИ не является архитектором,
имеющим право изменять фундамент системы.

---

# 14. Правило эскалации

Если предлагаемое решение требует:

- нарушения инварианта
- создания двойной истины
- переписывания истории
- изменения архитектурного фундамента

ИИ обязан явно указать:

> «Требуется изменение архитектурного фундамента».

Неявные изменения запрещены.
