# Architecture Constitution

Данный документ является архитектурной конституцией системы  
и фиксирует неизменяемые принципы разработки.

Документ утверждён до начала реализации
и имеет приоритет над кодом и контекстной документацией.

---

# 1. Архитектурная модель

Система строится на основе:

- Domain-Driven Design (DDD)
- Event Sourcing
- CQRS
- Append-only Event Store
- API-first
- Модульный монолит (не microservices)
- Single Object v1 (SaaS-ready)

---

# 2. Слои системы

Система строго разделена на 4 слоя:

1. Domain
2. Application
3. Infrastructure
4. Interface

Нарушение границ слоёв запрещено.

---

## 2.1 Domain Layer

Отвечает за:

- агрегаты
- доменные события
- инварианты
- value objects

Domain:

- не знает о БД
- не знает о HTTP / UI
- не знает о FULL_MODE
- не знает о System Mode
- не знает о ролях
- не знает об интеграциях
- не содержит SQL
- не содержит async I/O

---

## 2.2 Application Layer

Отвечает за:

- обработку команд
- orchestration
- FULL_MODE
- System Mode
- RBAC
- Conflict control
- expected_version
- публикацию событий

Application:

- не содержит бизнес-модели
- не содержит SQL
- не пишет напрямую в БД
- не загружает несколько агрегатов в рамках одной команды

Обязательное правило:

> Одна команда — один агрегат — одна транзакция

---

## 2.3 Infrastructure Layer

Отвечает за:

- Event Store
- проекции
- БД
- Celery
- интеграции
- сериализацию
- snapshot
- конфигурацию

Infrastructure:

- не принимает бизнес-решений
- не проверяет FULL_MODE
- не проверяет RBAC
- не генерирует доменные события самостоятельно

---

## 2.4 Interface Layer

Отвечает за:

- HTTP API
- CLI
- UI

Interface:

- не содержит бизнес-логики
- не принимает решений
- не проверяет инварианты

---

# 3. Event Sourcing

- Любое изменение состояния = новое событие
- События неизменяемы
- UPDATE и DELETE запрещены
- Event Store — единственная точка истины
- replay обязан быть детерминированным
- expected_version обязателен

Rollback состояния запрещён.

---

# 4. Запрет прямой записи событий

Ни один компонент системы не имеет права писать события напрямую в Event Store,
кроме Application Layer.

Запрещено:

- писать события из Celery напрямую
- писать события из интеграций напрямую
- писать события из Infrastructure
- писать события из Interface

Любая запись событий проходит через:

Application → Domain → Event Store

---

# 5. FULL_MODE

FULL_MODE:

- применяется только в Application Layer
- не известен Domain Layer
- не отключается OFFLINE
- создаёт событие PaymentVerificationRequired
- не может быть обойдён RECEPTION

---

# 6. System Mode

System Mode:

- является глобальным состоянием
- не является доменным событием
- не создаёт событий при смене
- проверяется только в Application

READ_ONLY:

- запрещает все write-команды
- запрещает override
- запрещает compensating события
- имеет приоритет над FULL_MODE

Celery-задачи обязаны проходить через Application Layer
и соблюдать System Mode.

---

# 7. Override

Override:

- создаёт отдельное событие
- не изменяет прошлые события
- не продолжает операцию автоматически
- требует повторного выполнения команды
- подлежит мониторингу

Автоматический override запрещён.

---

# 8. Конфликтная модель

Конфликт:

- является событием
- не удаляется
- не перезаписывается
- имеет severity:
  - BLOCKING
  - WARNING
  - INFO

Только BLOCKING блокирует операции.

Для BLOCKING устанавливается SLA.

---

# 9. Проекции

Проекции:

- строятся асинхронно
- не являются источником истины
- могут быть пересобраны
- обязаны быть idempotent
- обязаны учитывать aggregate_version
- не содержат бизнес-логики
- не проверяют инварианты

---

# 10. Snapshot

Snapshot:

- создаётся по policy (после N событий)
- содержит aggregate_version
- не является источником истины
- может быть удалён
- не влияет на юридическую историю

---

# 11. OFFLINE

OFFLINE:

- не отменяет append-only
- не допускает rollback
- не отключает FULL_MODE
- может создавать конфликты
- не является альтернативой System Mode

---

# 12. Технологический стек (утверждён)

Backend:
- Python 3.12
- FastAPI
- SQLAlchemy Async
- PostgreSQL
- Celery + Redis
- Pydantic
- Docker

Frontend:
- React + TypeScript
- Vite
- Zustand
- TanStack Query
- Tailwind + shadcn

Альтернативные технологии не рассматриваются.

---

# 13. Архитектурные запреты

Запрещено:

- писать бизнес-логику вне Domain
- писать SQL вне Infrastructure
- писать события вне Application
- игнорировать expected_version
- загружать несколько агрегатов в одной команде
- создавать технические события в Domain
- обходить System Mode
- обходить FULL_MODE

---

# 14. Изменение архитектуры

Любое изменение принципов:

- фиксируется в документации
- проходит архитектурное согласование
- не нарушает Event Sourcing
- не нарушает слоистую изоляцию

---

# 15. Заключение

Архитектура является:

- строгой
- юридически устойчивой
- детерминированной
- SaaS-ready
- модульной
- масштабируемой

Основной риск — дисциплина реализации.

Соблюдение данного документа обязательно.
