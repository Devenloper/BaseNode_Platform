# Application Layer Rules

Данный документ фиксирует обязательные правила реализации
Application Layer.

Документ является нормативным.
Нарушение правил считается архитектурной ошибкой.

---

# 1. Назначение Application Layer

Application Layer отвечает за:

- обработку команд;
- orchestration use-cases;
- применение системных политик;
- проверку RBAC;
- проверку FULL_MODE;
- проверку System Mode;
- контроль конфликтов;
- управление транзакцией;
- публикацию событий.

Application Layer **не содержит бизнес-модели**.

---

# 2. Главное правило

> Одна команда — один агрегат — одна транзакция.

Запрещено:

- загружать два агрегата в рамках одной команды;
- записывать события двух агрегатов в одной транзакции;
- координировать агрегаты напрямую.

Межконтекстная координация осуществляется
только через события.

---

# 3. Command Handling Model

Каждая команда проходит следующие этапы:

1. Проверка System Mode
2. Проверка RBAC
3. Проверка FULL_MODE (если применимо)
4. Загрузка агрегата
5. Проверка expected_version
6. Выполнение доменной операции
7. Получение доменных событий
8. Запись событий в Event Store
9. Публикация событий в Event Bus

Нарушение порядка недопустимо.

---

# 4. Декомпозиция Application Layer

Application Layer обязан быть структурирован:

- commands
- handlers
- guards
- policies
- services
- dispatcher

## 4.1 Handler

Handler:

- координирует use-case;
- работает с одним агрегатом;
- не содержит SQL;
- не содержит бизнес-правил;
- не принимает решений вне своей зоны.

## 4.2 Guard

Guard:

- проверяет допустимость выполнения;
- не изменяет состояние;
- не порождает события;
- не содержит доменной логики.

Примеры:
- system_mode_guard
- rbac_guard
- full_mode_guard

## 4.3 Policy

Policy:

- описывает правила orchestration;
- не содержит бизнес-инвариантов;
- не взаимодействует с БД напрямую;
- не заменяет Domain.

## 4.4 Service

Application Service:

- координирует инфраструктурные вызовы;
- не реализует бизнес-логику;
- не принимает окончательных решений.

## 4.5 Dispatcher

Dispatcher:

- централизует вызов handlers;
- не содержит бизнес-логики;
- не принимает решений.

---

# 5. Запрет бизнес-логики вне Domain

Запрещено:

- реализовывать инварианты в Application;
- проверять допустимость бизнес-операции в Guard;
- рассчитывать доменные состояния в Policy;
- дублировать инварианты из Domain.

Application может проверять только:

- режимы;
- роли;
- лицензии;
- системные ограничения.

---

# 6. Работа с Event Store

Application Layer:

- является единственной точкой записи событий;
- обязан передавать expected_version;
- обязан использовать optimistic locking;
- не имеет права игнорировать конфликт версий.

Запись событий напрямую из Infrastructure запрещена.

---

# 7. Конфликтная модель

Application:

- фиксирует конфликты как события;
- не удаляет конфликты;
- не перезаписывает события;
- не разрешает конфликты автоматически.

Override:

- создаёт отдельное событие;
- не продолжает команду автоматически.

---

# 8. FULL_MODE

FULL_MODE:

- проверяется только в Application;
- не известен Domain;
- не обходится RECEPTION;
- создаёт событие PaymentVerificationRequired.

---

# 9. System Mode

Application:

- обязан проверять System Mode до выполнения команды;
- обязан блокировать write-команды при READ_ONLY;
- обязан блокировать override при READ_ONLY.

Celery-задачи обязаны использовать Application Layer.

---

# 10. OFFLINE

Application:

- не меняет модель Event Sourcing;
- не отключает FULL_MODE;
- не обходит System Mode;
- допускает создание конфликтов;
- сохраняет causation_id и correlation_id.

---

# 11. Асинхронность

Application:

- не выполняет долгие операции синхронно;
- не вызывает внешние сервисы внутри транзакции;
- не блокирует запись событий.

Интеграции выполняются после фиксации событий.

---

# 12. Типичные нарушения

Архитектурными ошибками считаются:

- загрузка нескольких агрегатов;
- запись событий вне handler;
- SQL в Application;
- бизнес-логика в Guard;
- дублирование инвариантов;
- обход Dispatcher;
- вызов Event Store напрямую.

---

# 13. Критерий корректности

Application Layer реализован корректно, если:

- каждая команда работает с одним агрегатом;
- порядок обработки соблюдается;
- события записываются только через Application;
- Domain полностью изолирован;
- нет дублирования бизнес-логики.

---

# 14. Заключение

Application Layer — самая чувствительная часть архитектуры.

Он должен быть:

- строгим;
- минималистичным;
- дисциплинированным;
- предсказуемым.

Основной риск — превращение Application
в god-layer.

Соблюдение данного документа обязательно.
