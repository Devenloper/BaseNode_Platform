# Event Sourcing

Данный документ описывает обязательную модель Event Sourcing,
используемую в системе.

Документ является нормативным и обязателен к соблюдению.
Нарушение правил считается архитектурной ошибкой.

---

## 1. Основной принцип

Система использует Event Sourcing как единственный способ
фиксации изменений состояния.

> **Event Store — единственный source of truth.**

Состояние агрегатов **не хранится напрямую**  
и всегда может быть восстановлено из истории событий.

---

## 2. Событие

Событие — это:

- доменный факт;
- произошедший в прошлом;
- неизменяемый;
- юридически интерпретируемый;
- детерминированный.

Событие **не является**:
- командой;
- запросом;
- техническим логом;
- временным состоянием.

---

## 3. Append-only модель

Event Store работает строго в режиме append-only.

Запрещено:

- UPDATE событий;
- DELETE событий;
- overwrite payload;
- “исправление” истории.

Любое изменение состояния — **новое событие**.

Rollback состояния запрещён.

---

## 4. Структура события

Каждое событие обязано содержать:

- `event_id`
- `aggregate_id`
- `aggregate_type`
- `aggregate_version`
- `event_type`
- `event_version`
- `timestamp` (UTC)
- `payload`
- `metadata`

Metadata включает:
- `causation_id`
- `correlation_id`
- `actor`
- `source`

---

## 5. Версионирование и согласованность

Используется optimistic locking.

Правила:

- каждая команда передаёт `expected_version`;
- несовпадение версии приводит к конфликту;
- silent overwrite запрещён.

Игнорирование `expected_version`
считается критической архитектурной ошибкой.

---

## 6. Восстановление состояния (Replay)

Состояние агрегата восстанавливается путём:

1. загрузки snapshot (если есть);
2. последовательного применения событий;
3. строгого порядка по `aggregate_version`.

Replay обязан быть:

- детерминированным;
- воспроизводимым;
- независимым от внешних систем;
- одинаковым в OFFLINE и ONLINE режимах.

---

## 7. Граница ответственности слоёв

### Domain Layer
- порождает события;
- применяет события;
- не знает, где они хранятся.

### Application Layer
- orchestrates команды;
- проверяет `expected_version`;
- применяет System Mode / FULL_MODE;
- передаёт события в Event Store.

### Infrastructure Layer
- хранит события;
- сериализует;
- публикует;
- не принимает решений.

---

## 8. Запрет прямой записи событий

Запрещено писать события напрямую:

- из Infrastructure;
- из Celery;
- из интеграций;
- из UI;
- из проекций.

**Единственная точка записи событий — Application Layer.**

Нарушение приводит к обходу:
- System Mode;
- FULL_MODE;
- RBAC;
- conflict model.

---

## 9. Проекции (Read Model)

Проекции:

- строятся асинхронно;
- не являются source of truth;
- могут быть удалены и пересобраны;
- допускают eventual consistency.

Обязательные правила:

- проекция хранит `last_processed_event_version`;
- обработка должна быть idempotent;
- ordering основан на `aggregate_version`;
- бизнес-логика в проекциях запрещена;
- инварианты в проекциях запрещены.

---

## 10. Snapshot

Snapshot используется **только для оптимизации**.

Правила:

- snapshot не является источником истины;
- snapshot создаётся по policy (после N событий);
- snapshot содержит `aggregate_version`;
- snapshot может быть удалён без потери целостности;
- события всегда приоритетнее snapshot.

---

## 11. Компенсация ошибок

Ошибки **не исправляются задним числом**.

Используются:

- компенсирующие события;
- override события;
- конфликтная модель.

Rollback состояния запрещён.

---

## 12. OFFLINE и Event Sourcing

OFFLINE режим:

- не отменяет append-only;
- не допускает rollback;
- может создавать конфликты;
- требует корректных `causation_id` и `correlation_id`;
- не меняет модель replay.

OFFLINE не является альтернативой Event Sourcing.

---

## 13. READ_ONLY и Event Store

При READ_ONLY:

- запрещены все write-команды;
- запрещены override;
- запрещены compensating события;
- Celery-задачи не имеют права писать события.

Event Store остаётся неизменным.

---

## 14. Типичные нарушения

Архитектурными ошибками считаются:

- запись событий напрямую из Celery;
- бизнес-логика в проекциях;
- отсутствие `expected_version`;
- технические события в домене;
- изменение payload старых событий;
- replay, зависящий от внешних сервисов.

---

## 15. Критерий корректности реализации

Event Sourcing реализован корректно, если:

- любой агрегат можно восстановить с нуля;
- replay всегда даёт одинаковый результат;
- история читаема через годы;
- события юридически интерпретируемы;
- отсутствуют обходы Application Layer.

---

## 16. Заключение

Event Sourcing — фундамент архитектуры.

Он обеспечивает:
- детерминизм;
- аудит;
- юридическую устойчивость;
- масштабируемость;
- OFFLINE-устойчивость.

Любое упрощение Event Sourcing
не является оптимизацией и запрещено.
