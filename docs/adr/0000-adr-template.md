## 1. Context

Опишите архитектурный контекст, в котором принимается решение.

- Какая проблема решается?
- Почему текущее состояние недостаточно?
- Какие ограничения уже существуют (Core Frozen, Boundary Contracts и т.д.)?
- Какие риски или деградации возможны без этого решения?

Важно:
Контекст должен быть объективным.
Без эмоций.
Без альтернативных реализаций на этом этапе.

---

## 2. Decision

Чётко и однозначно зафиксируйте принятое решение.

Формулировка должна быть:

- недвусмысленной
- проверяемой
- архитектурно измеримой
- без "возможно", "скорее всего", "по ситуации"

Пример формата:

> Принято решение ...
>  
> Это означает, что ...
>  
> Запрещено ...
>  
> Обязательно ...

Decision — это нормативная часть ADR.

---

## 3. Rationale

Почему принято именно это решение?

- Какие альтернативы рассматривались?
- Почему они отвергнуты?
- Какие принципы лежат в основе (например: Event Sourcing, Isolation, Determinism)?
- Как решение защищает архитектуру?

Здесь допускается аргументация.
Но без переписывания Decision.

# Acceptance Criteria

ADR считается принятым, если:

- [ ] Статус установлен в Accepted
- [ ] Решение не противоречит Core Frozen v1
- [ ] Решение не нарушает Boundary Contracts
- [ ] Добавлены необходимые enforcement-механизмы (если требуется)
- [ ] ADR пронумерован корректно

---

# Lifecycle

- Proposed → обсуждается
- Accepted → является нормативным
- Rejected → не применяется
- Superseded → заменён другим ADR

---

# Architectural Integrity Rule

Любое изменение, противоречащее Accepted ADR,
требует нового ADR.

Изменение кода без изменения ADR —
архитектурное нарушение.
