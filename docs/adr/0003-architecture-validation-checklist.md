## 1. Context

После фиксации **Core Frozen v1** и **Boundary Contracts**
архитектура системы стала формально определённой,
но оставалась проблема **человеческого фактора**:

- разные ревьюеры проверяют архитектуру по-разному
- архитектурные нарушения обнаруживаются поздно
- часть нарушений выглядит «незначительной» на ревью
- отсутствует единый контрольный список для проверки

Без формализованного чеклиста:

- архитектурные правила применяются непоследовательно
- code review становится субъективным
- CI не имеет чёткого источника требований
- Core Frozen и Boundary Contracts теряют практическую силу

Необходим **единый нормативный документ**,
который определяет, *что именно* и *как* проверяется
при разработке, ревью и релизе.

---

## 2. Decision

Принято решение ввести **Architecture Validation Checklist**
как обязательный и нормативный инструмент архитектурной проверки.

Checklist:

- охватывает все слои системы
- основан на Core Frozen v1 и Boundary Contracts
- используется:
  - при code review
  - при добавлении новых фич
  - перед релизом
  - при рефакторинге
  - при архитектурном аудите

Checklist является **единственным источником правды**
для архитектурной валидации.

---

### 2.1 Область охвата Checklist

Checklist обязан проверять:

- соблюдение Core Frozen v1
- соблюдение Boundary Contracts
- корректность Event Sourcing
- корректность UnitOfWork
- корректность Outbox
- корректность optimistic locking
- изоляцию слоёв
- корректность read endpoint (v1)

Checklist не проверяет:

- бизнес-логику
- функциональные требования
- UX
- производительность (в v1)

---

### 2.2 Обязательность применения

Architecture Validation Checklist:

- **обязателен** для каждого PR
- **обязателен** перед релизом
- **обязателен** при любом изменении архитектуры
- **обязателен** при затрагивании write-модели

PR не может быть принят,
если checklist не пройден.

---

## 3. Rationale

Checklist введён для:

- устранения субъективности code review
- формализации архитектурных требований
- защиты Core Frozen v1
- обеспечения повторяемости проверок
- упрощения CI enforcement
- снижения архитектурного долга

Альтернативы:

- «проверять на глаз» → отвергнуто (не масштабируется)
- «полагаться на CI» → отвергнуто (CI не покрывает всё)
- «архитектор проверяет всё» → отвергнуто (узкое место)

Checklist — минимально достаточный механизм,
который связывает ADR → CI → Code Review.

---

## 4. Consequences

### 4.1 Положительные последствия

- архитектурные правила становятся проверяемыми
- ревью становится объективным
- новые участники быстрее входят в проект
- CI имеет чёткую спецификацию
- архитектурные отклонения выявляются рано

---

### 4.2 Ограничения

- увеличивается формальность процесса
- PR требует больше дисциплины
- нельзя «быстро починить» в обход правил
- часть проверок остаётся ручной

Эти ограничения считаются приемлемыми
для защиты архитектуры.

---

### 4.3 Архитектурные обязательства

После принятия ADR-0003:

- каждый PR обязан ссылаться на checklist
- checklist должен обновляться при изменении архитектуры
- новые архитектурные правила → новый пункт checklist
- CI enforcement обязан соответствовать checklist
- отсутствие checklist = блокирующий дефект

---

## 5. Enforcement

Architecture Validation Checklist enforce’ится через:

- PR checklist (обязательный шаблон)
- code review (manual gate)
- CI Boundary Enforcement (ADR-0004)
- архитектурные аудиты

Checklist является связующим звеном
между ADR и CI.

Если правило отсутствует в checklist —
оно не считается enforce’имым.

---

## 6. Notes

Checklist актуален для **Core Frozen v1**.

При переходе к Core Frozen v2:

- checklist должен быть пересмотрен
- старый checklist архивируется
- новый checklist фиксируется отдельным ADR

# Architectural Integrity Rule

Если архитектурное правило:

- не описано в ADR
- не включено в checklist
- не enforce’ится

→ оно не считается частью архитектуры.

Архитектура существует
только в том, что проверяется.
