## 1. Context

После фиксации:

- Core Frozen v1  
- Boundary Contracts  
- Architecture Validation Checklist  
- CI Boundary Enforcement  

архитектура системы формально защищена на уровне:

- контрактов
- зависимостей
- процессов
- CI

Однако остаётся риск деградации через изменение
**структуры репозитория**:

- добавление новых верхнеуровневых директорий
- появление “shared”, “common”, “utils”
- смешивание слоёв
- появление параллельных application/domain
- перенос инфраструктуры в корень
- неявное расширение архитектуры без ADR

Структура репозитория является отражением архитектуры.

Если структура не зафиксирована —
архитектура постепенно размывается.

---

## 2. Decision

Принято решение зафиксировать структуру репозитория
как часть архитектурного контракта.

### 2.1 Разрешённая структура (Core v1)

Корневой уровень репозитория может содержать только:

- `domain/`
- `application/`
- `infrastructure/`
- `interface/`
- `contracts/`
- `docs/`
- `docs/adr/`
- служебные файлы конфигурации (pyproject, CI, etc.)

Любые новые верхнеуровневые директории запрещены
без нового ADR.

---

### 2.2 Структурные ограничения

Запрещено:

- добавлять `shared/`
- добавлять `common/`
- добавлять `helpers/`
- добавлять `utils/`
- добавлять параллельные слои
- перемещать существующие слои
- смешивать код слоёв
- создавать альтернативную архитектурную структуру

Любое изменение структуры слоёв
считается архитектурным изменением.

---

### 2.3 Статус структуры

Структура репозитория:

- является частью архитектуры
- является нормативной
- подлежит CI-проверке
- не может изменяться без нового ADR

---

## 3. Rationale

Repository Structure Lock необходим для:

- предотвращения хаотического роста проекта
- предотвращения скрытого смешивания слоёв
- защиты Boundary Contracts
- обеспечения предсказуемости архитектуры
- снижения архитектурного долга

Альтернативы:

- «доверять разработчикам» → отвергнуто  
- «проверять на ревью» → недостаточно  
- «не фиксировать структуру» → приводит к деградации  

Структура — это не организационный вопрос,
а архитектурный контракт.

---

## 4. Consequences

### 4.1 Положительные последствия

- структура проекта становится стабильной
- новые разработчики видят ясную модель
- CI может проверять архитектурную форму
- снижается риск архитектурного расползания
- архитектура становится самодокументируемой

---

### 4.2 Ограничения

- нельзя быстро добавить “временную папку”
- нельзя экспериментировать со слоями без ADR
- реорганизация требует формального решения
- увеличивается дисциплина разработки

Ограничения считаются приемлемыми
для защиты архитектуры.

---

### 4.3 Архитектурные обязательства

После принятия ADR-0005:

- CI обязан проверять верхнеуровневую структуру
- PR не может изменять структуру без ADR
- появление новой директории = блокирующий дефект
- изменение структуры требует нового ADR

---

## 5. Enforcement

Repository Structure Lock enforce’ится через:

- CI job проверки структуры
- Protected branch policy
- PR checklist
- Architecture Validation Checklist
- Code review

CI обязан:

- проверять допустимые root директории
- завершаться с ошибкой при появлении новых

Структурное нарушение = CI failure.

---

## 6. Non-Goals

ADR-0005:

- не фиксирует внутреннюю структуру внутри слоёв
- не запрещает рефакторинг внутри слоя
- не запрещает добавление новых агрегатов
- не запрещает добавление новых use-case
- не ограничивает read-model

Ограничение касается только архитектурного уровня.

без формального архитектурного решения,

архитектура перестаёт быть архитектурой.

часть архитектурного контракта.
