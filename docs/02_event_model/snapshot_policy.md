# Snapshot Policy

Данный документ описывает правила создания, хранения
и использования snapshot в системе Event Sourcing.

Документ является нормативным.
Нарушение правил считается архитектурной ошибкой.

---

## 1. Назначение snapshot

Snapshot используется **исключительно для оптимизации**:

- ускорения replay агрегатов;
- снижения времени cold-start;
- уменьшения нагрузки при восстановлении состояния.

> Snapshot **не является источником истины**.

Единственный source of truth — Event Store.

---

## 2. Что такое snapshot

Snapshot — это сохранённое состояние агрегата
на определённой версии событий.

Snapshot:
- является производным артефактом;
- может быть удалён;
- может быть пересоздан;
- не влияет на юридическую историю.

---

## 3. Что snapshot НЕ делает

Snapshot:

- не заменяет события;
- не отменяет replay;
- не участвует в бизнес-логике;
- не используется для принятия решений;
- не используется в Domain Layer напрямую.

---

## 4. Граница ответственности

### Domain Layer
- не знает о snapshot;
- не использует snapshot;
- не содержит snapshot-логики.

### Application Layer
- инициирует загрузку агрегата;
- не принимает решений на основе snapshot.

### Infrastructure Layer
- хранит snapshot;
- управляет созданием и удалением;
- оптимизирует загрузку агрегатов.

---

## 5. Snapshot как оптимизация replay

Процесс восстановления агрегата:

1. загрузка snapshot (если есть);
2. загрузка событий **строго после snapshot_version**;
3. последовательное применение событий.

Если snapshot отсутствует — replay начинается с нуля.

---

## 6. Snapshot policy (когда создавать)

Snapshot создаётся:

- после **N событий** одного агрегата;
- значение N фиксировано политикой (например, 100–500);
- политика едина для всей системы или контекста.

Snapshot **не создаётся**:
- при каждом событии;
- условно по бизнес-логике;
- из Domain Layer.

---

## 7. Содержимое snapshot

Snapshot **обязан содержать**:

- aggregate_id
- aggregate_type
- aggregate_version
- сериализованное состояние агрегата
- timestamp создания

Snapshot **не должен содержать**:

- производные данные;
- данные проекции;
- внешние ссылки;
- временные вычисления.

---

## 8. Версионирование snapshot

Snapshot привязан к:

- версии агрегата;
- версии сериализации.

При изменении схемы агрегата:

- старые snapshot могут быть проигнорированы;
- replay продолжается с событий;
- корректность сохраняется.

---

## 9. Удаление snapshot

Snapshot может быть:

- удалён вручную;
- удалён автоматически;
- полностью очищен без потери данных.

Удаление snapshot:
- не нарушает Event Sourcing;
- не требует компенсации;
- не фиксируется как событие.

---

## 10. Snapshot и OFFLINE

OFFLINE режим:

- не меняет snapshot policy;
- не создаёт альтернативные snapshot;
- не нарушает replay.

Snapshot создаётся только на основе
подтверждённых событий.

---

## 11. Snapshot и READ_ONLY

READ_ONLY:

- запрещает запись событий;
- **не запрещает** чтение snapshot;
- **не запрещает** удаление snapshot;
- **не запрещает** rebuild агрегатов.

Snapshot — технический артефакт.

---

## 12. Типичные ошибки

Архитектурными ошибками считаются:

- использование snapshot как source of truth;
- принятие решений на основе snapshot;
- бизнес-логика при создании snapshot;
- хранение производных данных;
- отсутствие версии агрегата в snapshot;
- невозможность восстановить агрегат без snapshot.

---

## 13. Критерий корректности

Snapshot реализован корректно, если:

- агрегат можно восстановить без snapshot;
- snapshot можно удалить без последствий;
- replay всегда детерминирован;
- snapshot ускоряет, но не влияет на поведение;
- snapshot не участвует в бизнес-решениях.

---

## 14. Заключение

Snapshot — это ускоритель,
а не часть бизнес-модели.

Он должен:
- быть простым;
- быть заменяемым;
- быть безопасным;
- быть полностью вторичным.

Любое усложнение snapshot
является архитектурным дефектом.
