# Projection Rules

Данный документ описывает обязательные правила построения,
обработки и эксплуатации проекций (Read Model).

Документ является нормативным.
Нарушение правил считается архитектурной ошибкой.

---

## 1. Назначение проекций

Проекции предназначены **исключительно** для чтения данных.

Проекции:
- не являются источником истины;
- не участвуют в принятии бизнес-решений;
- могут быть удалены и пересобраны;
- допускают eventual consistency.

> Единственный source of truth — Event Store.

---

## 2. Граница ответственности

### Domain Layer
- не знает о проекциях;
- не использует проекции;
- не зависит от read-model.

### Application Layer
- не читает проекции для принятия решений;
- использует проекции только для query-операций.

### Infrastructure Layer
- реализует проекции;
- управляет их хранением и пересборкой;
- не содержит бизнес-логики.

---

## 3. Основное правило

> **Проекция — это производное представление событий, а не модель поведения.**

Любая логика в проекции — это дефект архитектуры.

---

## 4. Запрещённая логика в проекциях

В проекциях запрещено:

- бизнес-правила;
- проверки инвариантов;
- принятие решений;
- расчёт допустимости операций;
- агрегация, влияющая на поведение системы;
- условная логика, влияющая на команды.

Проекции не заменяют Domain и Application.

---

## 5. Event Processing Model

Проекции обрабатывают события:

- асинхронно;
- последовательно по версии агрегата;
- независимо друг от друга.

Проекция **не имеет права**:
- пропускать события;
- менять порядок обработки;
- обрабатывать события выборочно.

---

## 6. Version-based processing

Каждая проекция обязана:

- хранить `last_processed_event_version` для каждого агрегата;
- обрабатывать события строго по `aggregate_version`;
- отклонять события с меньшей или равной версией;
- обеспечивать детерминированный порядок.

Version-based processing обязателен.

---

## 7. Idempotency

Обработка события в проекции должна быть **idempotent**.

Требования:

- повторная обработка события допустима;
- результат повторной обработки идентичен;
- side effects запрещены;
- отсутствие idempotency считается дефектом.

---

## 8. Ordering

Порядок обработки:

- определяется `aggregate_version`;
- не зависит от времени доставки;
- не зависит от очереди;
- не зависит от retry механизма.

Нарушение ordering разрушает консистентность read-model.

---

## 9. Rebuild проекций

Проекции должны поддерживать:

- полную пересборку с нуля;
- пересборку по диапазону событий;
- безопасный rebuild без остановки системы.

Rebuild:
- не создаёт событий;
- не влияет на Domain;
- не нарушает append-only.

---

## 10. Проекции и Celery

Celery используется для:

- асинхронной обработки событий;
- масштабирования read-model;
- retry механизмов.

Celery-задачи:
- не пишут события;
- не обходят Application Layer;
- не принимают решений.

---

## 11. Проекции и System Mode

System Mode:

- не влияет на обработку проекций;
- не останавливает rebuild;
- не изменяет replay.

READ_ONLY:
- запрещает write-команды;
- **не запрещает** обновление проекций.

---

## 12. Проекции и OFFLINE

OFFLINE режим:

- может задерживать доставку событий;
- не меняет порядок;
- не отменяет replay;
- не создаёт альтернативных состояний.

Проекция должна корректно догонять отставание.

---

## 13. Типичные нарушения

Архитектурными ошибками считаются:

- бизнес-логика в проекции;
- вычисление разрешений в read-model;
- отсутствие version-based обработки;
- зависимость от времени доставки;
- запись событий из проекции;
- side effects (HTTP, write-команды).

---

## 14. Критерий корректности

Проекция реализована корректно, если:

- может быть удалена без потери данных;
- может быть пересобрана с нуля;
- всегда даёт один и тот же результат;
- не влияет на поведение системы;
- не содержит бизнес-логики.

---

## 15. Заключение

Проекции — это удобство чтения,
а не часть бизнес-модели.

Любая попытка использовать проекцию
как источник решений
является нарушением архитектуры.
