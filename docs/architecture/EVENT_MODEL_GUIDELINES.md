# 1. Назначение

Настоящий документ определяет правила проектирования, версионирования и эволюции доменных событий.

Документ обязателен для всех доменов системы.

Нарушение данных правил приводит к архитектурной деградации и потере воспроизводимости системы.

---

# 2. Общие принципы

## 2.1 Событие — это факт

Событие отражает уже произошедший факт.

Событие:

- Не является командой
- Не является объяснением
- Не является намерением
- Не может быть отменено
- Не может быть изменено

Событие фиксирует:

> "Это произошло"

---

## 2.2 Событие неизменяемо

После записи в Event Store:

- payload нельзя изменять
- тип события нельзя менять
- timestamp нельзя корректировать
- actor нельзя переписывать

Исправление допускается только через новое событие.

---

## 2.3 Событие должно быть детерминированным

Событие должно быть:

- Воспроизводимым
- Идемпотентным
- Однозначно интерпретируемым

Replay всех событий должен приводить к идентичному состоянию агрегата.

---

# 3. Структура события

Каждое событие обязано содержать следующие поля:

## 3.1 Метаданные

- event_id (UUID)
- aggregate_id
- aggregate_type
- event_type
- version (версия агрегата)
- timestamp (UTC)
- actor
- correlation_id
- causation_id
- external_event_id (если применимо)
- tenant_id

## 3.2 Payload

payload содержит только доменные данные.

Правила:

- payload не должен содержать вычисляемых данных
- payload не должен содержать дублирующих read-model значений
- payload должен быть минимальным, но достаточным

---

# 4. Правила именования событий

## 4.1 Событие именуется в прошедшем времени

Примеры:

- BookingCreated
- PaymentRecorded
- GuestPassportUpdated
- ConflictDetected
- LoyaltyPointsAccrued

Запрещено:

- CreateBooking
- UpdatePayment
- FixGuest
- ProcessSomething

---

## 4.2 Событие должно быть атомарным

Одно событие — один факт.

Нельзя:

- объединять несколько логических фактов
- создавать универсальные события типа DataUpdated

---

# 5. Версионирование событий

## 5.1 Когда требуется новая версия

Новая версия события требуется, если:

- добавлено обязательное поле
- изменена структура payload
- изменена семантика поля
- изменён формат данных

---

## 5.2 Upcasting

Система обязана поддерживать upcasting:

- Старые события должны быть преобразованы в новую структуру
- Replay старых событий не должен ломаться
- Старые версии не удаляются

---

## 5.3 Запрещено

- Изменять смысл существующего поля
- Переиспользовать event_type для нового смысла
- Удалять поле из payload без версии

---

# 6. Компенсирующие события

## 6.1 Исправление ошибок

Если необходимо исправить ранее зафиксированный факт:

- Создаётся новое событие
- В нём указывается compensation_for_event_id
- Старое событие остаётся неизменным

---

## 6.2 Нельзя

- Удалять ошибочное событие
- Редактировать ошибочное событие
- Перезаписывать агрегат

---

# 7. Взаимосвязь событий

## 7.1 causation_id

Указывает, какое событие вызвало текущее.

Обязателен для всех внутренних реакций.

---

## 7.2 correlation_id

Используется для объединения событий в одну бизнес-цепочку.

Например:

Бронирование → Оплата → Подтверждение

---

## 7.3 external_event_id

Используется для:

- Webhooks
- PMS sync
- Внешних API

Система обязана:

- Хранить обработанные external_event_id
- Игнорировать дубликаты
- Логировать повторную попытку

---

# 8. OFFLINE-события

## 8.1 Требования

В OFFLINE:

- event_id должен быть детерминированным
- Повторная синхронизация не должна создавать дубликаты
- Порядок событий сохраняется

---

## 8.2 Запрещено

- Генерировать новый event_id при sync
- Пересоздавать событие
- Автоматически откатывать локальные события

---

# 9. Аудит и безопасность

События, связанные с:

- Просмотром ПДн
- Финансовыми операциями
- Изменением ролей
- Закрытием периода

Обязаны фиксироваться как доменные события.

Скрытое логирование без события запрещено.

---

# 10. Производные данные

В событии запрещено хранить:

- агрегированные суммы
- вычисленные итоги
- производные показатели
- кэшированные значения

Эти данные относятся к read-модели.

---

# 11. Ограничения эволюции

Запрещено:

- Менять event_type существующего события
- Изменять payload задним числом
- Переписывать историю
- Переинтерпретировать старые события

Если изменилась бизнес-логика — создаётся новая версия события.

---

# 12. Тестирование событий

Каждый домен обязан иметь:

- Тест replay агрегата
- Тест версии события
- Тест upcasting
- Тест идемпотентности
- Тест concurrency

Без теста replay событие не считается валидным.

---

# 13. Контроль через Core Guardian

Любое изменение:

- структуры события
- payload
- правил версионирования
- компенсации

Требует согласования с Core Architecture Guardian и создания ADR.

---

# 14. Главный принцип

История системы — это последовательность событий.

Если replay не воспроизводит состояние — архитектура нарушена.

События — это закон.
