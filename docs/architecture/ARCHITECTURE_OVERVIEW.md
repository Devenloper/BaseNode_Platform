Документ фиксирует:

- Архитектурную парадигму
- Инварианты системы
- Границы доменов
- Принципы событийной модели
- Конфликтную модель

# 2. Архитектурная парадигма

Система строится на основе:

- Domain-Driven Design (DDD)
- Event Sourcing
- CQRS
- Append-only Event Store
- Optimistic Concurrency Control
- Anti-Corruption Layer (для внешних систем)
- Outbox Pattern (для интеграций)
- Eventual Consistency
- Отсутствия распределённых транзакций

---

# 3. Ключевые инварианты

Ниже приведены правила, которые не могут быть нарушены.

## 3.1 Неизменяемость

- События неизменяемы.
- Запрещены UPDATE доменных данных.
- Запрещено удаление доменных событий.
- Исправление выполняется только через компенсирующее событие.

## 3.2 Единственный источник истины

Каждый домен имеет один источник истины:

- Проживание — PMS
- Услуги — локальная система
- Лояльность — локальная система
- HR — локальная система
- ДГУ — локальная система

Дублирование источников истины запрещено.

## 3.3 Отсутствие «тихих исправлений»

Любое изменение должно порождать доменное событие.

Любой override допускается только через событие:
OverrideApplied с указанием причины и инициатора.

## 3.4 Запрет распределённых транзакций

- Агрегат атомарен только в пределах своей границы.
- Кросс-доменные изменения выполняются через события.
- Прямая запись в несколько агрегатов одной транзакцией запрещена.

## 3.5 Event Store — единственный источник истины

- Event Store работает в режиме append-only.
- Прямой доступ к Event Store запрещён.
- Запись событий возможна только через Command-слой.
- Read-model являются производными проекциями и могут быть пересобраны.

# 4. Событийная модель

Каждое событие обязано содержать:

- event_id (UUID)
- aggregate_id
- aggregate_type
- event_type
- payload (JSON)
- version (версия агрегата)
- timestamp (UTC)
- actor
- correlation_id
- causation_id
- external_event_id (для интеграций)
- tenant_id

Правила:

- timestamp фиксируется в момент создания события.
- События должны быть воспроизводимы (replay).
- Эволюция структуры события требует версионирования.
- Изменение структуры — через новую версию события и upcasting.
- Изменение смысла ранее записанных данных запрещено.

---

# 5. Командная модель

Изменение состояния происходит через:

Команда → Валидация → Доменное событие

Команда содержит:

- command_id
- aggregate_id
- expected_version
- actor
- timestamp
- payload

Правила:

- Команда не может изменять более одного агрегата.
- При нарушении инварианта создаётся Rejected Event.
- Состояние не может быть изменено без создания события.

---

# 6. Версионирование и конкурентный доступ

- Каждый агрегат имеет поле version.
- Команда обязана передавать expected_version.
- При расхождении версий создаётся ConcurrencyConflictDetected.
- Silent overwrite запрещён.

---

# 7. Конфликтная модель

Конфликты являются сущностью первого класса.

Примеры:

- BookingConflict
- PaymentConflict
- PMSConflict
- RiskConflict
- UnitConflict
- FiscalConflict
- FuelConflict
- MaintenanceConflict

Правила:

- Конфликт фиксируется событием.
- Конфликт имеет статус.
- Конфликт не устраняется автоматически.
- Разрешение конфликта требует события ConflictResolutionApplied.

---

# 8. OFFLINE-модель

Система поддерживает деградированный режим работы.

В OFFLINE:

- События сохраняются локально.
- event_id должен быть детерминированным.
- Идемпотентность обязательна.
- Запрещён автоматический rollback локальных событий.
- Синхронизация выполняется строго в порядке создания.

После восстановления связи:

- Выполняется детерминированная синхронизация.
- Проверяется версия агрегатов.
- При расхождении создаётся Conflict.
- Ранее зафиксированные OFFLINE события не отменяются.

Для проживания:

- Создание брони OFFLINE запрещено.
- Подтверждение брони OFFLINE запрещено.

# 9. Границы доменов

Система разделена на независимые bounded context:

- Booking
- Guest
- Finance
- Loyalty
- Unit
- Employee
- Task
- DGU
- Analytics
- Integration

Правила:

- Домены не имеют прямого доступа к БД друг друга.
- Взаимодействие происходит только через события.

---

# 10. Финансовые инварианты

- Сумма операции не может быть изменена задним числом.
- Платёж не может быть удалён.
- Возврат выполняется только через компенсирующее событие.
- Валовая и чистая выручка разделены.
- Закрытый финансовый период не может быть изменён.

---

# 11. Защита данных и юридическая устойчивость

Система должна обеспечивать:

- Защиту персональных данных
- Неизменяемый аудит
- Трассируемость финансовых операций
- Соответствие миграционным требованиям
- Невозможность скрытого изменения данных

Правила:

- Аудит является append-only.
- Доступ к ПДн логируется.
- Массовая выгрузка невозможна без события.
- Юридически значимые выгрузки формируются только из событий.

---

# 12. Принципы read-моделей

- Read-model являются производными проекциями.
- Могут быть пересобраны из Event Store.
- Не участвуют в проверке инвариантов.
- Допускается eventual consistency (до 5 секунд ONLINE).
- Пересборка не изменяет события.

---

# 13. Архитектурные запреты

Строго запрещено:

- Прямое редактирование БД
- Скрытые исправления
- Бизнес-логика в read-модели
- Изменение payload события после записи
- Отключение аудита
- Отключение конфликтов
- Использование серверного времени для изменения прошлого
- Распределённые транзакции

---

# 14. Масштабируемость

Система:

- Горизонтально масштабируема
- Поддерживает разделение read/write
- Поддерживает outbox-паттерн
- Восстанавливается через replay
- RPO ≤ 15 минут
- RTO ≤ 1 час

Рекомендуемая эксплуатация — до 100 активных сотрудников на инсталляцию.

---

# 15. Управление архитектурой

Изменения, затрагивающие:

- Структуру события
- Инварианты агрегата
- Конфликтную модель
- OFFLINE-поведение
- Командную модель

Требуют:

- Создания ADR
- Обновления версии документа
- Проверки совместимости
- Проверки replay

Документ не может быть изменён под давлением срочности бизнеса.
